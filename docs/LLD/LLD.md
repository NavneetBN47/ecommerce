# COMPREHENSIVE BACKEND ENGINEERING SPECIFICATION PACKAGE\n## Shopping Cart System - SCRUM-96\n\n---\n\n## EXECUTIVE SUMMARY\n\nThis document provides a complete backend engineering specification for the Shopping Cart System (SCRUM-96), a Spring Boot MVC application supporting user management, product search, and shopping cart operations. The system enforces strict business rules at both service and database levels, maintains stateless authentication, and ensures carts do not persist across logout sessions.\n\n**Key Highlights:**\n- **Architecture**: Spring Boot MVC (Controller → Service → Repository)\n- **Database**: Relational database with enforced constraints\n- **Core Domains**: User Management, Product Catalog, Shopping Cart Management\n- **APIs**: 11 RESTful endpoints covering all functional requirements\n- **Business Rules**: 15+ validation rules enforced at multiple layers\n- **Lifecycle Management**: Lazy cart creation, auto-deletion on empty, cleanup on logout\n\n**Scope Boundaries:**\n- ✅ In Scope: User CRUD, Authentication, Product Search, Cart Operations\n- ❌ Out of Scope: Checkout, Payments, Inventory Locking, Admin Management, Password Changes\n\n---\n\n## DETAILED ANALYSIS\n\n### 1. DOMAIN IDENTIFICATION\n\nBased on the Jira story analysis, the system comprises four primary domain entities:\n\n#### 1.1 User Domain\n**Purpose**: Manage user accounts and authentication\n**Lifecycle**: Created on sign-up, persists indefinitely, profile updatable\n**Key Rules**: \n- Username uniqueness enforced at database level\n- Stateless authentication (no session persistence)\n- Username immutability post-creation\n\n#### 1.2 Product Domain\n**Purpose**: Represent searchable catalog items\n**Lifecycle**: Pre-seeded, read-only for users\n**Key Rules**:\n- Product existence required before cart operations\n- Price immutability through user actions\n- Case-insensitive search capability\n\n#### 1.3 Cart Domain\n**Purpose**: Container for user's shopping selections\n**Lifecycle**: Lazy creation on first add, auto-deletion when empty or on logout\n**Key Rules**:\n- One active cart per user maximum\n- Cannot exist without cart items\n- Must be deleted on logout\n\n#### 1.4 CartItem Domain\n**Purpose**: Line items within a cart\n**Lifecycle**: Created on add, updated on quantity change, deleted on remove\n**Key Rules**:\n- Quantity must be > 0\n- Belongs to exactly one cart\n- Product must exist\n\n### 2. FUNCTIONAL REQUIREMENTS BREAKDOWN\n\n#### 2.1 User Management (4 APIs)\n1. **Sign-Up**: Register new user with validation\n2. **Sign-In**: Authenticate and return user details\n3. **View Profile**: Retrieve user information\n4. **Update Profile**: Modify mutable fields (full name, email)\n\n#### 2.2 Product Catalog (1 API)\n1. **Search Products**: Keyword-based, case-insensitive search\n\n#### 2.3 Shopping Cart Management (6 APIs)\n1. **Add Product to Cart**: Lazy cart creation, item addition\n2. **Update Cart Item Quantity**: Modify existing item quantity\n3. **Remove Product from Cart**: Delete specific item, auto-delete cart if empty\n4. **View Cart**: Display all items with totals\n5. **Clear Cart**: Remove all items and cart (implicit on logout)\n6. **Logout with Cart Cleanup**: Delete cart and items\n\n### 3. DATA INTEGRITY CONSTRAINTS\n\n#### Database-Level Constraints:\n- **UNIQUE**: users.username\n- **NOT NULL**: All primary keys, foreign keys, required fields\n- **FOREIGN KEY**: cart.user_id → users.id, cart_item.cart_id → cart.id, cart_item.product_id → products.id\n- **CHECK**: cart_item.quantity > 0\n- **CASCADE DELETE**: cart deletion → cart_items deletion\n\n#### Application-Level Validations:\n- Username format and length\n- Email format validation\n- Password strength (implementation-specific)\n- Quantity positivity\n- Product existence before operations\n- User existence before cart operations\n\n---\n\n## DELIVERABLES\n\n### DELIVERABLE 1: DOMAIN ENTITIES AND ATTRIBUTES\n\n#### Entity 1: User\n```\nEntity Name: User\nTable Name: users\nPurpose: Store user account
